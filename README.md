# VETTED: vendor onboarding, from submission to a reasoned decision

Zamp AI Solutions Analyst case study, PS-2. A vendor submits company details, bank details, tax registration and documents; VETTED checks everything and returns **Approved**, **Pending** or **Rejected** with every check visible. When something is missing, it tells the vendor exactly what and gives them a link to fix only that.

**Live:** https://vetted-onboarding.vercel.app · Sibling project for PS-1 (invoices): https://verity-ap.vercel.app

## The idea in one line

**AI reads, rules decide.** Gemini reads the documents (even scans) and writes the explanations; deterministic code does every check and makes every decision. Same submission, same answer, every time.

## The 10 stages

| # | Stage | By | What it does |
|---|---|---|---|
| 1 | Receive submission | Code | Form and documents in, each file fingerprinted (SHA-256) |
| 2 | Completeness | Code | Required fields and documents for this business type (MSME needs Udyam) |
| 3 | Read documents | AI | Gemini reads GST certificate, PAN card, cheque; flags a file that isn't what it claims; evidence check against the PDF text layer |
| 4 | Format checks | Code | GSTIN check digit, PAN format and holder type, IFSC, PIN vs state, free webmail |
| 5 | Cross-check | AI + code | PAN inside GSTIN, GST state vs address, names across form/GST/PAN, business type vs PAN 4th character and GST constitution, cheque vs form |
| 6 | Verify externally | Code | GST registry status and legal name (simulated), **live IFSC directory lookup**, bank account holder via penny drop (simulated) |
| 7 | Fraud & duplicates | Code | Bank account already used by another vendor, GSTIN already a vendor, blocklist, shared phone/email |
| 8 | Decide | Code | Findings → Approved / Pending (vendor or reviewer) / Rejected, plus a 0–100 risk score and custom rules |
| 9 | Communicate | AI | Reviewer summary and the vendor email: an exact numbered ask with the fix link (fraud rejections never reveal what was detected) |
| 10 | Record | Code | Vendor created in the vendor master on approval, case timeline, audit trail |

Finding severities: **reject** (never onboard) · **vendor** (the vendor must fix or send something, so they get the fix link) · **review** (a person here decides) · **info** (note only).

## The 10 test submissions (`public/samples/`)

| # | Type | Scenario | Outcome |
|---|---|---|---|
| v01 | Smooth path | Clean private limited company, documents consistent, MSME certificate | ✅ Approved |
| v02 | Edge case | Bank account is in the name SUNDARAM TRADERS, not the company | ⏸ Pending: vendor gives an account in the company's name |
| v03 | Edge case | GSTIN carries another taxpayer's PAN and legal name | ❌ Rejected |
| v04 | Edge case | GST registration cancelled; vendor sent an old certificate | ❌ Rejected |
| v05 | Edge case | Bank account already belongs to approved vendor Kaveri Office Supplies | ❌ Rejected (fraud; email reveals nothing) |
| v06 | Edge case | Second PAN card uploaded where the cancelled cheque should be | ⏸ Pending: upload the cheque |
| v07 | Approved, with a twist | Trades as LNE Office Interiors; legal identity consistent | ✅ Approved + note |
| v08 | Approved, with a twist | Sole proprietor, account in owner's name, scanned documents | ✅ Approved + note |
| v09 | Edge case | Declared Private Limited; PAN and GST say Partnership | ⏸ Pending: confirm business type |
| v10 | Edge case | No single failure, but registered 18 days ago + Gmail + no sponsor = risk 60 | ⏸ Pending: reviewer decides |

**The loop:** open v02's (or v06's / v09's) fix link, click *Use the sample correction*, resubmit: round 2 is approved and the vendor gets an ID.

Documents are fictional specimens marked "SPECIMEN · TEST DATA", generated by `scripts/build_samples.py`.

## Also built in

- **Vendor portal** (`/apply`): public registration form with live GSTIN check-digit, PAN-in-GSTIN and IFSC branch lookups as you type.
- **Fix link** (`/fix/<case>`): the vendor sees only their asks, fixes them, and resubmits; documents already read are reused, only new ones are read.
- **Reviewer actions**: approve (creates the vendor), reject, or ask the vendor a specific question (goes back on the fix link).
- **Custom rules**: IF / THEN policies by dropdown or in plain English (Gemini drafts, a person confirms). Rules can review, reject or note, never approve.
- **Decision record**: printable one-page record per case (Save as PDF). **CSV export** on the dashboard.
- Saved readings as a fallback so a demo never stalls if Gemini is unavailable (always labelled).

## Stack

Next.js 15 on Vercel · Gemini API (`gemini-3.5-flash` reads documents, Flash-Lite for short text tasks, with fallback between models) · Supabase Postgres with row-level security: every table only accepts requests carrying a server-only secret header, so the browser never holds a database credential · Server-Sent Events for the live run view.

## Running it

```bash
npm install
cp .env.example .env.local   # GEMINI_API_KEY; optional SUPABASE_URL, SUPABASE_ANON_KEY, VETTED_DB_KEY
npm run dev
```

Without a Gemini key the 10 samples use their saved readings; without Supabase, data is kept in memory. `npm run samples` regenerates the test submissions.

## Assumptions

- Buyer: Northwind Retail India, Chennai. Vendors are Indian GST-registered businesses.
- The vendor master is shared with accounts payable (the same one VERITY pays from).
- GST registry and penny-drop responses are simulated with realistic data; in production they are a GST Suvidha Provider API and the bank's API. IFSC lookups are real.
- Nothing uncertain is approved silently: it goes back to the vendor (an exact ask) or to a reviewer (a judgement call).
- For a sole proprietorship, an account in the proprietor's own name is acceptable.
